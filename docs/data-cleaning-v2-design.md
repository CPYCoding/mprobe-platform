# Dataset Cleaning & Poison Detection — 重新設計指南（v2）

> 這份文件取代前兩份（`data-cleaning-integration-plan.md`、`data-cleaning-implementation-guide.md`）。那兩份是基於「把 `data_washing_experiment` 三支腳本直接搬進來、每次現場訓練」這個設計寫的，經過一輪實測後，發現這個架構有根本問題（見下方），所以整個重新設計。

## 一、先搞懂：這種服務本質上在做什麼

「Dataset Cleaning & Poison Detection」要回答的問題只有一個：**給一批資料，哪幾筆可能被動過手腳（貼了後門觸發器）？**

回答這個問題，業界/學界大致分兩條路：

1. **樣式比對（signature matching）**：如果你已經知道攻擊者用的觸發器長什麼樣、貼在哪，直接逐筆比對像素，命中就是中毒。不需要訓練任何模型，純統計比對，快、準、穩定（前提是你真的知道觸發器長怎樣）。**完全不需要「看過」這筆資料**——任何全新、從沒見過的圖片都能直接檢查，因為比對的是固定已知的觸發器樣式，不是靠訓練認出這張圖。
2. **行為異常偵測（behavioral / feature anomaly）**：不知道觸發器長怎樣時，靠一個「知道什麼是正常資料長什麼樣」的模型，去看每筆資料的特徵/行為跟正常資料差多少，異常就標記。這條路一定要有一個訓練過的模型當「正常的基準」——但訓練的是「什麼是正常」這個通用標準，不是記住特定資料，所以一樣可以用在全新、沒被訓練過的資料上。

兩條路都合理，也都有其位置——差別在於**該由誰訓練、什麼時候訓練**，這是我們這輪繞了一大圈才搞清楚的關鍵。

## 二、我們實測後發現的根本問題（別再犯）

之前的做法是：`clean_reference`、`blind_feature` 這兩個方法，**每次使用者按下「執行清洗」，才現場從零訓練一個小模型**。實測後發現三個致命傷：

- **慢**：大規模跑一次要 10 幾分鐘。
- **不穩定**：同樣的程式碼、同樣的資料規模，只換一個隨機種子，準確率可以從 0% 跳到 63.6%——代表結果幾乎是隨機的，不能拿去做正式判斷。
- **貴**：每個使用者請求都要重新耗運算資源訓練，沒辦法規模化服務。

正確的做法應該是：**訓練只做一次，離線做，訓練完存成模型檔案（`.pt`）；線上服務只做推論（inference），讀取這個固定的模型檔案去打分數，不重新訓練**。這才是「樣式比對」（`materialized`，本來就沒有訓練這個問題）跟「行為異常偵測」都應該有的正確架構。

## 三、`data_washing_experiment` 三個方法，該怎麼用

**要不要直接拿來用？答案是：核心邏輯可以參考/沿用，但架構要大改，而且三個的定位不一樣：**

### `materialized_trigger_detector`（樣式比對）——保留，當正式功能的核心 / 第一層
不需要訓練，架構本來就對。唯一要補的是：讓它能吃「使用者上傳的任意資料集」（不是只能吃 CIFAR-10），觸發器庫要能擴充（不只紅色方塊），圖片尺寸不同要能自動換算比對位置。這個可以直接當 V1 正式上線的主力功能，對完全沒看過的新資料一樣有效。

### `blind_feature_detector`（特徵異常偵測）——邏輯保留，架構要重做 / 第二層
原本的問題不是演算法本身錯，是「每次現場訓練」這個做法。正確做法：**離線訓練一次一個通用的特徵抽取模型**（用夠大、夠多樣的資料訓練，不要每次都用使用者那一小包參照資料現場訓練），存成模型檔，上線後固定使用這個模型算特徵距離。使用者提供的參照資料，只拿來做**便宜的統計校準**（算門檻用的分位數），不要拿去訓練整個網路。這樣結果才會穩定、可重現、夠快。

定位建議：因為它是唯一不需要事先知道觸發器的方法，概念上最有價值，能對付第一層抓不到的未知型態攻擊，但準確率目前只有 ~40% 左右，**先定位成「輔助訊號，標記給人工複審」，不要當自動判定/自動刪除的依據**。**只對第一層(materialized)沒抓到的剩餘資料跑**，避免重複運算已經確定的威脅。

### `clean_reference_detector`（觸發已知圖案測信心變化）——不建議投資做成正式功能
理由：它一定要「已知觸發器」這個前提，這點跟 `materialized` 一樣，但 `materialized` 直接比對像素、又快又準，`clean_reference` 繞了一大圈去測模型反應（還要每次重新訓練一個小 CNN），效果反而更差、更不穩定，沒有互補的價值——已知觸發器的情況，`materialized` 早就先抓走了，輪不到它。而且它歷史上表現好的數字（56-77% F1），部分來自原始論文聯邦學習實驗裡「多個 client 資料結構本身不同」這個線索，這個線索在「使用者上傳單一資料集」的真實情境裡根本不存在，就算花大工重現也沒有實質意義。建議只留在展示頁面當**教育性質的效果對照**（誠實呈現「不知道觸發器樣子時，這條路線有多弱」），不要投入工程資源把它產品化。

## 四、正確的系統架構

```
離線（一次性，不是每次請求都做）:
  訓練資料 → 訓練特徵抽取模型 → 驗證效果穩定 → 存成 detector_model.pt

線上服務（每次使用者請求，只做推論）:
  使用者上傳資料集（全新、沒被訓練過的資料）
    → 第一層 [已知觸發器庫比對] materialized，全自動、快、準
    → 第二層 [對第一層剩下的資料，用固定特徵模型算異常分數] blind_feature，標記可疑、送複審
    → 產出：
       - 確認乾淨（兩層都沒標記）
       - 自動移除（第一層高信心比對到已知觸發器）
       - 待複審（第二層標記的異常，不自動移除）
       + 稽核報告
```

沒有「中毒比例滑桿」——那個只該存在於另一個獨立的「效果展示 / 沙盒測試」頁面，讓潛在客戶自己控制注入已知程度的攻擊去驗證工具真的有用（類似防毒軟體業界的 EICAR 測試檔案概念），跟「上傳真實資料集」這條正式服務流程要分開，不要混在同一個介面。

## 五、稽核報告欄位設計

- **基本資訊**：`scan_id`、`dataset_name`、`dataset_hash`（綁定這份報告對應的就是這一份資料，防止事後偷換）、`scan_timestamp`、`detector_version`
- **總結判定**：`total_samples`、`total_flagged`、`overall_verdict`
- **分偵測器結果（一定要分開列，不要混成一個籠統數字）**：
  ```json
  "detectors": [
    {
      "name": "materialized_trigger_match",
      "confidence": "high",
      "known_triggers_checked": ["red_square_v1", "logo_watermark_v1"],
      "flagged_count": 12,
      "flagged_sample_ids": [...]
    },
    {
      "name": "blind_feature_anomaly",
      "confidence": "advisory_only",
      "description": "Statistical anomaly vs. clean feature baseline — recommended for human review, not automatic removal.",
      "flagged_count": 47,
      "flagged_sample_ids": [...]
    }
  ]
  ```
- **逐筆明細**：`sample_id`、`flagged_by`、`reason`、`recommended_action`（auto_remove / review / keep）
- **誠實揭露範圍限制**：明確聲明「本次掃描僅檢查平台已知觸發器庫中的樣式，無法保證偵測到全新型態的後門攻擊」，並列出各偵測器已知準確率區間
- **簽章**：`report_signature`（Ed25519）、`signing_key_id`，供買家獨立驗證報告未被竄改
- **下載連結**：`cleaned_dataset_download_url`、`raw_report_json_url`

## 六、V1 建議實作順序

1. **先把 `materialized` 改成能吃任意上傳資料集**（不限 CIFAR-10）：處理任意圖片尺寸、支援 zip 上傳、觸發器庫可設定。這個最快能上線，風險最低。
2. **把 `blind_feature` 的特徵模型改成離線訓練 + 線上固定推論**：這步驟本身就能順便解決穩定性問題。訓練一次、驗證效果穩定後存檔，上線後不要再現場訓練。
3. 兩層串接：第一層跑完，剩下的資料才給第二層跑。
4. 產出格式統一：不管哪個策略，輸出都是「N 筆總數、M 筆被標記為可疑、可疑清單、可下載的清洗後資料集、稽核報告」——真實上傳的資料沒有標準答案，不會有 precision/recall/F1 這些數字，這點要跟現有 demo 頁面（合成沙盒模式，有中毒比例滑桿）的呈現方式分開。
5. `clean_reference` 保留在現有的效果展示 demo 頁面即可，不用 migrate 進正式服務。
6. 之後有餘力，再考慮補上「清洗後資料重新訓練 + 拿已知觸發器做行為驗證」這個閉環（可以沿用平台自己已經寫過的 `apply_trigger`/`build_trigger_pair` 邏輯來產生測試樣本，不需要 GitHub 那支綁死聯邦學習框架的 `poison_audit.py`）。對應你最早查看的 `mprobe_40_model.tar` vs `baseline_40_model.pt` 那組防禦前後對照，這是這整條產品線邏輯上該有的終點。
